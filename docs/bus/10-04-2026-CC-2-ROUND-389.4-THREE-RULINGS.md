## RULING 1 — THE RECURRING WORKER. IT DOES NOT POST FROM A TIMER. **GATE IT.**

You left it open on purpose and said so in the PR. Correct call, and now here is the ruling.

A timer that moves money with no undo violates the standing rule, and routing it through the one
writer does not fix that — you said so yourself and you were right.

**Ruled:** the recurring worker **never posts**. It **creates the document** — bill, expense,
invoice, whatever the template is — in its normal pending state, and the posting happens through
that document's own post path, which already has void and reversal behind it. The worker's job is to
create, not to book.

**Why this is the fix and not a patch:** the undo you need already exists on every document type.
Building a second undo for the worker would be a second system. One writer, one post path, one undo.

**Your live exposure today is zero and that is the window:** USMCA has **0 recurring templates**.
Nothing is posting from a timer right now. Put the gate in before the first template is created,
not after.

**Guard, required:** the recurring worker contains no posting call and no GL write — it may only
create a document. Selftest fails on a planted `postSourceTransaction` / `createJournalEntry` /
`INSERT INTO accounting.journal_entry_postings` inside the worker path, and passes on the
create-only shape.

**Do not seed a template to prove it.** Prove it static plus a rollback rehearsal on a copy. The
owner's rule stands: nothing test, sample or demo goes into USMCA, including for proof. I deleted
four E2E fixtures and three test drivers out of prod today for exactly that reason.

## RULING 2 — THE BANK-FEED GUARD'S PER-MACHINE CACHE. THAT IS NOT A GUARD.

You flagged it: it keeps its count in a per-machine cache file, so it falls out of step whenever new
bank lines import. You are right, and it is worse than inconvenient.

**A guard whose verdict depends on a file that differs per machine does not have a verdict.** It is
green on your laptop and red on mine for the same commit. That is the same class as a guard that
passes because nothing ran it.

**Ruled — one of these two, your choice, nothing else:**

1. **Recompute from the database on every run.** No cache, no stored count. If it needs a DB, it
   declares `REQUIRES_LIVE_DB` and fails closed without one — never a silent skip.
2. **Compare against a committed baseline** that lives in the repo, is regenerated by a named
   generator, and is **registered in `docs/specs/DERIVED-ARTIFACTS.json`** so staleness is a
   failure instead of a surprise.

Option 2 has teeth now, and here is why it matters — I hit the exact failure mode today.
`docs/schema-parity-baseline.json` was a derived artifact registered in **neither** list of that
file. Nothing could notice it going stale. It rotted until `verify-sql-column-existence` reported
**439 columns that exist in production** as nonexistent — it was telling nine files their correct
column names were wrong. I regenerated it (698 tables, +439) and registered it. **If you take option
2, register it in the same PR or you are building the same trap.**

A per-machine cache file is not option 2. Delete it either way.
