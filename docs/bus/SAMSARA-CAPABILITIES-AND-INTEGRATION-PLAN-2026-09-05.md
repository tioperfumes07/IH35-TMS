## 1. The owner's question — "do we auto-create a Samsara place/geofence when we book a load, and get real mileage?"
**Measured answer: the code path exists; it has never produced a single row.**
- Code: `apps/backend/src/dispatch/loads.routes.ts:1616` → `autoCreateGeofencesForLoad` (`telematics/auto-geofence.service.ts`) → inserts `geo.geofences` (square around the stop) → outbox event `samsara.create_geofence` → `outbox/handlers/samsara-create-geofence.handler.ts:65` → `api.createAddress()` (Samsara `POST /addresses`).
- Live (Neon, USMCA, 15:35Z): `geo.geofences` = **2** (Mines Rd yard, a TEST fence), created today **0**, `samsara_address_id` **null on both**; `outbox.outbox_queue` has **0** `samsara.create_geofence` events ever; `integrations.samsara_addresses` = **0 rows** (the X.9 import service deployed 13:29Z has not run); `mdata.load_stops` for the 57 live loads: **0 of 114 carry latitude/longitude, 1 of 114 carries a `location_id`**.
- Why nothing happens: (a) the hook fires only on the HTTP Book Load route — only **6** loads went through it (6 `dispatch.load.created` events); the seeded loads went through the service layer and skipped the hook; (b) even on the HTTP path the stop has no coordinates, so there is nothing to draw a fence around; (c) the Samsara push handler has never been exercised (0 events), so it is unproven.
- Real mileage: `samsara-client.ts:382` already pulls `gps,engineStates,obdOdometerMeters,fuelPercents,obdEngineSeconds`; `telematics.vehicle_locations.odometer_mi` is populated. What is missing is the **stop → fence → odometer-at-entry/exit → leg miles** chain, and Samsara's own `stops.actualDistanceMeters` (only exists if we push loads as Samsara routes).

## 3. Build vs use — the decision the owner asked for
- **Use Samsara Routes for arrival / departure / on-time / leg miles.** Push each dispatched USMCA load as a Samsara route at Dispatch (not at Book), stops as `singleUseLocation` from the geocoded stop (or `addressId` when the site exists in Samsara), `externalIds {"ih35Load","ih35Stop"}`, on-time window from the stop's appointment window, BOL/POD form required on the delivery stop. Consume `RouteStopArrival/Departure/EarlyLateArrival`, `DocumentSubmitted`, and `stops.actualDistanceMeters` back into `mdata.load_stops.actual_arrival_at/actual_departure_at` (`actual_arrival_source='samsara'`), `docs.files`, and the leg-miles table. This retires most of what the in-house geofence engine was rebuilt to do for arrivals, while our engine stays for the yard/Love's/border fences and the **driver prompt/answer** (Samsara cannot require an answer).
- **Keep and finish our side of real miles:** odometer at stop arrival/departure from `stats/feed` decorations → `PRACTICAL / SHORT / REAL DRIVEN` per load (law §2), cross-checked against `actualDistanceMeters` and `hos/daily-logs.distanceTraveled`.
- **Fix the Book Load address flow first (prerequisite for both):** every stop must carry lat/lng + a `mdata.locations` row (X.9 gives us Samsara's 255 addresses as candidates; the wizard's address picker must offer them and write `location_id`), and the geofence/Samsara-address creation must run from the **service layer** (so seeds and API both trigger it), not only from the HTTP route.
