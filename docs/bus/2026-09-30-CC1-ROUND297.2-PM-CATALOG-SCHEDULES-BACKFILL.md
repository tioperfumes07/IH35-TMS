## A-29 — owner backfill route

`apps/backend/src/maintenance/service-history-backfill.routes.ts` (new) —
`POST /api/v1/maintenance/service-history`. In one transaction: (1) a
`maintenance.work_orders` row, `status='complete'`, `source_type='backfill'`, (2) a
`telematics.odometer_readings` row, `source='manual'`, `confidence='entered'`, (3) — only when
`pm_code` names a real, active schedule row for that unit — that schedule's
`last_service_odometer`/`next_due_odometer` are set (the latter only for a `miles`-kind interval; a
`days`/`hours`-kind interval has no mileage-based due date in this schema and none is invented).
Idempotent on `(operating_company_id, unit_id, service_date, pm_code)`, checked inside the same
transaction before any insert (409 on a real duplicate).

AP linkage reuses the existing poster a live work-order completion already calls
(`processMaintenanceWorkOrderClose`, `apps/backend/src/accounting/maintenance-posting/poster.service.ts`)
— called after this route's own transaction commits (the poster reads `maintenance.work_orders` on
its own connection). No new bill-posting logic was written — "six reversal engines exist; a seventh
must not be written."

Two small, additive schema gaps found and closed while building this, both DDL-only, no data
touched:
- `maintenance.work_orders.source_type`'s CHECK only allowed `('IS','ES','AC','ET','RT','IT','RS')`
  — the order's own literal spec (`source_type='backfill'`) wasn't a legal value. Widened via
  `202614810000_work_orders_backfill_source_type.sql` to add `'backfill'`; the 4 already-live values
  (16 real rows: IS×10, RS×2, IT×2, AC×2) are untouched.
- `maintenance.work_order_lines.section` is `character(1)` (existing real values `'A'`/`'B'`, a
  print-layout section code, not a semantic field) — the route writes `'A'`.

Registered in `apps/backend/src/index.ts` (route registration only, per LANES.md SHARED convention).

## GUARD

`scripts/verify-pm-schedule-never-guesses-a-baseline.mjs` (verify-step 11961). Static checks: (a)
`last_service_odometer` is never derived from a current-odometer column, (b) no writer targets
`maint.pm_schedule`, (c) the work-orders insert and the odometer-readings insert both exist in the
same route file (never one without the other), (d) `next_due_odometer` never appears in a
statement window without `last_service_odometer` alongside it. Live check: zero
`maintenance.pm_schedules` rows anywhere have `next_due_odometer` set while `last_service_odometer`
is NULL. `--selftest`: 4/4 planted defects rejected. Live run: PASS.
