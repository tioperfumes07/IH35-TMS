C25 gl_delta — "C25 GL Δ"                                          APPROVED
-------------------------------------------------------------------------------
Every money-moving action on the leaf writes a balanced journal entry, and the
GL delta equals the amount the surface displayed.
PROOF SHAPE: kind sql. Create through the live UI, then assert on the resulting
entry: sum(debit_amount) = sum(credit_amount), AND the net movement on the
target account equals the amount rendered. Two assertions, both required.
A leaf that moves no money is NA, not PASS.

C26 subledger_tie — "C26 Subledger"                                APPROVED
-------------------------------------------------------------------------------
The module's subledger total ties to its GL control account for a stated period.
AR subledger = AR control. AP subledger = AP control. Driver escrow subledger =
escrow liability control. Bank register = cash control.
PROOF SHAPE: kind sql, returning (subledger_sum - control_sum) and asserting 0.
The period must be named in the proof, not implied.

C27 lifecycle_complete — "C27 Lifecycle"                           APPROVED
-------------------------------------------------------------------------------
Every status the record can hold is reachable, and every terminal status either
posts or reverses. No status may strand money.
PROOF SHAPE: kind sql or dom. Enumerate the statuses from the enum or check
constraint — not from a hand-written list — and show the GL effect of each
transition, all exercised. A status that exists in the database and is not in
the proof is an automatic FAIL.

-------------------------------------------------------------------------------
C28 reversal_symmetry — "C28 Reversal"                             APPROVED
-------------------------------------------------------------------------------
Voiding or reversing a posted transaction writes an equal and opposite entry.
It never deletes and never edits the original. Debits and credits swap. The
original stays readable forever.
PROOF SHAPE: kind sql. Post, reverse, then assert: two entries exist, they net
to zero, and the original row is unchanged (same id, same amounts, same
created_at). This is WORM and it is already our law — void by UUID, never
DELETE a financial row.

C29 period_guard — "C29 Period"                                    APPROVED
-------------------------------------------------------------------------------
No transaction may post into a closed accounting period, by anyone. Reopening
is owner-only and is recorded with who, when, and why.
STANDARD: NetSuite states a closed period "prevents posting to the general
ledger for any dates included in the period, by anyone," and keeps system notes
as the audit trail. That is the bar. QuickBooks does the same through the
closing date and password.
PROOF SHAPE: kind mutation. Close a period, then ATTEMPT a post into it and
assert the write is REFUSED. A guard that does not reject when defeated is not
a guard — the proof engine already tests for exactly this.
STATUS: UNBUILDABLE TODAY. There is no period close in the backend. All 16 C29
cells stay red until Cursor ships it in its own dedicated session. Correct as-is.

C30 entity_isolation — "C30 Entity"                                APPROVED
-------------------------------------------------------------------------------
A user scoped to TRANSP can never read or write a USMCA row. At the database
layer, through RLS — not by a filter in the UI.
PROOF SHAPE: kind sql, RLS ON, no bypass. Run the same query under each company
context and assert zero cross-entity rows.
HARD RULE: any proof for C30 that uses SET LOCAL app.bypass_rls is void on its
face. Bypass is a diagnostic tool for me and Claude reading prod; it can never
appear in a C30 proof. If it does, the cell is FAIL regardless of the result.

C31 non_empty_proof — "C31 Living doc"                CORRECTED, THEN APPROVED
-------------------------------------------------------------------------------
Cursor asked how C31 treats labeled TEST versus empty, because CREATE-TEST-THEN
-VOID says an empty TMS table is expected. Fair question, wrong premise. I read
prod. The tables are not empty:

    accounting.bills      16,327 rows        54 flagged is_sample_data
    accounting.expenses   27,237 rows       146 flagged
    accounting.payments   12,139 rows         6 flagged
    accounting.invoices   12,033 rows        17 flagged
    mdata.vendors          2,982 rows         3 flagged
    mdata.customers        2,739 rows         0 flagged
    accounting.journal_entries 2,214 rows   208 flagged
    (je_control 2214 on every query — RLS bypassed for the read, values real)

So emptiness is not our risk. The opposite is. C31 is therefore defined as:

  The surface returns count > 0 from PROD on the CURRENT live SHA. A labeled
  TEST row counts as a real row — that is the whole point of the law. Emptiness
  is only a C31 FAIL if the seat failed to create the TEST hop first, which is
  already forbidden by rule 5 of CREATE-TEST-THEN-VOID.

  AND — the half that actually protects the company — every TEST row carries
  is_sample_data = true, and every financial report excludes it: trial balance,
  P&L, balance sheet, cash flow, and register. Both halves, or C31 is FAIL.

PROOF SHAPE: kind sql + kind http. count > 0 on the live SHA, plus a second
assertion that the report query filters is_sample_data.
