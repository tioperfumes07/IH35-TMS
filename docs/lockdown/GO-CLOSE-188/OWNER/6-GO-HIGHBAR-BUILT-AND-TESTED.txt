THE SIX RULES — each one closes a way a green result could be a lie.
Not one is stylistic. Every one traces to a failure that already happened here.
===============================================================================
R1  A DISCRIMINATOR IS MANDATORY, AND IT RUNS FIRST, EVERY TIME.
    An RLS-scoped read that returns nothing satisfies "difference == 0" vacuously.
    That trap produced a false "zero reconciliation sessions exist" read on
    2026-08-30 and a false "board broken, 0/14" read before it. Both mine.
    A proof with no probe block is REJECTED at load — not failed, rejected, so it
    can never be mistaken for a passing assertion.

R1-b THE ZERO-ROWS HOLE.  This one nearly got past me.
    Half the invariants pass by returning NO rows (INV-4 documents with no GL,
    INV-6 stranded accounts, INV-10c duplicate roles). A discriminator cannot
    ride on a result set that is required to be empty. So zero rows from a blind
    read would have looked exactly like zero rows from a clean ledger, and the
    engine would have certified a ledger it could not see.
    Fixed: a separate INV-0 CONTROL block runs first on EVERY proof. If the probe
    cannot see the ledger, nothing after it is evidence of anything.

R2  AN EMPTY RESULT IS A FAIL, NEVER A PASS.
    "No rows" is the shape of both "clean" and "I could not see the data." Those
    must never map to the same verdict.

R3  NO INLINE SQL. The query comes from a committed .sql file, by block id.
    This is the closed-loop defence. If the query and the assertion live in one
    file, a seat chasing green can weaken the query and satisfy its own
    assertion, and no claim visibly changes.

R4  READ-ONLY, TWICE.
    Parsed for INSERT/UPDATE/DELETE/DROP/ALTER/GRANT/CREATE/COPY before
    connecting, then run inside BEGIN + SET TRANSACTION READ ONLY + ROLLBACK.
    A verifier that can write is a verifier that can fix its own evidence.

R5  bypass_rls IS FORBIDDEN IN AN ENTITY-ISOLATION PROOF.
    C30 asserts a TRANSP user cannot see a USMCA row. Bypassing RLS to check RLS
    is the purest closed loop available. Rejected at load.

R6  THE OBSERVED VALUE IS ALWAYS RECORDED, PASS OR FAIL.
    A verdict without the number it saw cannot be audited later.

PLUS one more the build itself forced:
    A MULTI-STATEMENT BLOCK IS REFUSED. INV-10 holds four sub-queries. Run whole,
    the driver returns only the LAST result — so a proof aimed at 10c would have
    been silently graded on 10d and nobody would ever have known. A proof must
    name its sub-query. C30 now names 10c explicitly.

THE CLOSED-LOOP DETECTOR — the guard that stops the class from returning
===============================================================================
The single most expensive pattern on this project, three appearances:
  1. verify-economic-columns-c25-c31-present read columns.shared.json and
     asserted the ids were in columns.shared.json. Printed OK while 28 of 29
     modules rendered no ECON group.
  2. The matrix proves a LEDGER column by text-matching LEDGER PROSE naming that
     column. Writing the sentence turns the cell green.
  3. DRV-S04: prose asserted PASS; the only reader of the prose was a human.

The rule it enforces: a verifier whose ONLY input is a spec under docs/ is a
DECLARATION RATCHET. Ratchets are useful — they stop a spec regressing. What
they are not is evidence a product behaves. So a ratchet must say so in its
header with @ratchet, and a @ratchet may NEVER back a Live / prod_verified claim.

I deliberately made it narrow. Reading one product source file is a source-read
guard, not a closed loop, and calling 3,500 honest guards defective would have
been a false accusation — the exact error this whole instrument exists to stop.
A verifier with no literal path is reported as UNKNOWN, never as guilty.

  RESULT ON THIS REPO: 7,029 verifiers · 29 UNDECLARED CLOSED LOOPS · 507 unknown
