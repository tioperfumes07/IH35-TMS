2. THE GAP THAT MAKES EVERYTHING ELSE UNUSABLE — nobody has named this yet
===============================================================================
This is my actual recommendation and it is not in your six points.

deriveStatus, proof-engine.mjs line ~105:

    if (!item.proven_at_sha || !liveSha || item.proven_at_sha !== liveSha)
      return { status: "STALE", ... };

EXACT SHA MATCH. Correct rule — a proof at an old SHA is not a proof about what
is running. But look at what it implies against how we actually ship:

    Deploys to prod, 2026-08-30 alone:
      626602b 03:52 · 84188fa 04:26 · 48e08e5 04:44 · 9c61c63 11:46
      15a190d 12:00 · b8fc09ce 14:59
    Six live-SHA changes in eleven hours.

EVERY PROOF IN THE REPO GOES STALE SIX TIMES A DAY.

And nothing re-runs them. I grepped: deriveStatus is called by selftest.mjs,
demo-live.mjs and shadow-report.mjs. That is all. Nothing in .github/workflows,
nothing in package.json, nothing in verify-module-completion.mjs. The proof engine
runs only when a human types the command.

So if you flip enforcement on today, here is what happens:
  1. Board goes green on the items that have proofs.
  2. Cursor deploys.
  3. Every item derives STALE. Board reads zero.
  4. The only way back is a human re-stamping proven_at_sha on every item —
     which is HAND-STAMPING, the exact thing the engine exists to abolish.
  5. Somebody turns enforcement off. Correctly. It is unusable.

An instrument that can never be switched on is a prototype, however good its
selftest is. 20/20 planted defects does not fix this.

THE FIX, AND THE HOST ALREADY EXISTS.
.github/workflows/prod-postdeploy-verify.yml already:
  - triggers on push to main
  - polls the Render API and WAITS for the deploy of THAT EXACT COMMIT to go live
  - holds RENDER_API_KEY
  - then smokes production

It is the replay loop, already built, already correct, and it does not know the
proof engine exists. Add one step to it:

    - name: Replay proofs at the live SHA
      env: { DATABASE_URL: ${{ secrets.PROD_READONLY_DATABASE_URL }} }
      run: node scripts/proof-engine/replay-all.mjs --live-sha "$SHA" --write

  replay-all.mjs: for every item with proofs[], replay through ctx.runSql /
  ctx.fetch / ctx.exec at the now-live SHA, write the DERIVED status,
  prod_verified and proven_at_sha, and commit the derived artifact.

  Then proven_at_sha is never typed by a person again. It is written by the job
  that watched the deploy go live. STALE stops being a daily catastrophe and
  becomes what it should be: the state of an item whose proof genuinely failed
  to re-run.

  The DATABASE_URL must be a READ-ONLY prod role. The runner enforces read-only
  twice (parse + SET TRANSACTION READ ONLY), but CI should not hold a writable
  prod credential regardless.

WITHOUT THIS STEP, DO NOT FLIP ENFORCEMENT. With it, enforcement is safe and the
shadow-mode disagreement count becomes a number that falls on its own as items
gain proofs — which is the metric that has been missing for forty days.
