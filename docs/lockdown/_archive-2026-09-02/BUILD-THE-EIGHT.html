IH35 · GO-20 · the eight half-built features

Build The Eight

All eight built fully. Two of them turned out not to need a table at all. Every one of the other six has real source data already sitting in production, so none of this is built beside the data — it is built on it.

Every foreign key target verified against the live database, September 2, 2026

The decision

Eight built, two blocked, two deferred

  • Build fully: bank drift, predictive maintenance, accident liabilities, cargo sensor incidents, workers compensation claims, work order parts, work order labor rates, driver late arrival rate.
  • Blocked: the QuickBooks and bank feed health checks. Both are already served correctly elsewhere and their endpoint already throws. The action is to delete the dead file and repoint the uptime monitor, not to build them.
  • Deferred to launch: cooling customers and recommended fuel stops. Neither may be left as a silent empty in the meantime — each reports itself unavailable or comes off its screen.
The finding

Two of the eight must not get a new table

Slices F and G look like missing tables and are not.

The parts data already lives in maintenance.parts_inventory and the labor rates already live in catalogs.labor_rates. Both are real, both are populated, and the code already falls back to them correctly and flags the fallback. Creating inventory.parts would add a whole schema to hold one duplicate table; creating maintenance.labor_rates would create a second rate list that disagrees with the first the day it ships. That is precisely the fragmentation the linkage law exists to prevent.

The real defect in both is on the screen, not in the database. The work order picker never reads the source status the backend is already returning, so a catalog that is unavailable looks exactly like a catalog with zero rows. Fix that and both slices are done, with no migration and one deleted stray file.

The other six

Every one has real source data already in production

This is what made the specification possible without guessing. The projections, the readings, the variances, the arrivals and the accident cost lines are all already being written. What was never built is the layer that turns them into something a person is told about.

The strongest single piece of evidence: insurance.claim already has a liability_id column.

It points at safety.accident_liabilities — a table nobody ever created. Beside it sit driver_responsible, deductible_cents, recovery_rail and deduction_id. The entire accident to liability to chargeback to insurance chain was designed, the columns were written to hold it, and one link in the middle was never built. That is why filing an accident today records the accident and decides nothing.

The eight

What each one is, and what gets built

A

Bank reconciliation drift alerts

CC-3New tablebanking.reconciliation_drift_alerts
What already exists

banking.reconciliation_sessions already computes and stores variance_cents, statement and book balances. The drift is being measured and nobody is ever told. The alert layer is the only missing piece.

What gets built

The detector opens an alert when a finalized session is outside tolerance, when a live bank balance disagrees with its ledger account, or when a feed goes stale past 24 hours. It never posts a journal entry. Resolving requires a written reason and records the correcting entry if one is made. Tolerance is a setting per bank account, not a constant.

B

Predictive maintenance alerts

CC-3New tablemaintenance.predictive_alerts
What already exists

maintenance.brake_projections and maintenance.tire_projections already hold projected_replacement_date and a wear rate per day for every position. The projection math is done and finished. Only the alerting was never built.

What gets built

A nightly job opens an alert when a projection falls inside the horizon, warning at 14 days and critical at 7. Creating a work order from an alert stamps the work order on it, so the unit history reads prediction then repair as one chain. The alert closes when a newer projection clears it or the work order closes.

C

Accident liabilities

CURSORNew tablesafety.accident_liabilities
What already exists

insurance.claim already carries a liability_id column pointing at a table nobody ever created, alongside driver_responsible, deductible_cents and deduction_id. safety.accidents and safety.accident_cost_lines are live. The whole chain was designed and this one link is missing.

What gets built

Filing an accident creates a liability with no decision and posts nothing. Only the owner decides, choosing driver chargeback, company absorbs, insurance only, or split, with a written note. A split must sum exactly to the net exposure. A chargeback creates a pending deduction that is never automatic and never silent. A liability with no decision never posts.

D

Cargo sensor incidents

CC-2New tabledispatch.cargo_sensor_incidents
What already exists

dispatch.cargo_sensor_readings already writes an out_of_range flag with temperature, humidity and door status against a load and trailer. Nothing groups those readings into an incident and nothing tells anybody.

What gets built

A watcher opens one incident on the first out-of-range reading, extends it while readings stay out, and closes it after a settling window — one incident per excursion, not one per reading. Thresholds come from the load or the customer, never a constant. It can be handed to a customer as a claim.

E

Workers compensation claims

CURSORNew tablesafety.workers_comp_claims
What already exists

safety.incidents already carries incident_type and an auto_created_claim_id column, and insurance.claim and insurance.policy are live. A driver files an injury today, is told it succeeded, and nothing is created.

What gets built

The injury branch stops skipping. If the claim cannot be created the submission fails loudly, because a driver must never be told an injury was filed when nothing was recorded. The open count stops returning zero when the table is missing and reports unavailable instead. The Safety Home indicator finally renders the count it has been parsing and throwing away.

F

Work order parts

CC-1No table — delete the phantommaintenance.parts_inventory
What already exists

maintenance.parts_inventory is live and already holds part number, description, category, on-hand quantity, location, reorder threshold and last purchase. The code already falls back to it and already flags the fallback correctly.

What gets built

Do not create inventory.parts. A schema holding one duplicate table is exactly the fragmentation the linkage law forbids. Delete the stray Prisma migration so nobody applies it later by accident, read the canonical table directly, and fix the real defect: the screen never reads the source status, so an unavailable catalog looks identical to zero parts.

G

Work order labor rates

CC-1No table — delete the phantomcatalogs.labor_rates
What already exists

catalogs.labor_rates is live with rate code, name, hourly rate and active flag, and it is already mounted as a generic catalog. The code already falls back to it correctly.

What gets built

Do not create maintenance.labor_rates. A second labor rate table would disagree with the first the day it shipped. Repoint the reader, and apply the same screen fix as the parts picker. One caution for the guard: the generic catalog registry uses that string as a catalog name, not a table name, so the guard must not trip on that line.

H

Driver late arrival rate

CC-3New tabledispatch.late_arrival_aggregates
What already exists

dispatch.stop_arrivals and mdata.load_stops already carry appointment windows, scheduled arrivals and actual arrivals. Everything needed to define late is already recorded.

What gets built

Late means arriving after the appointment window, or after the scheduled arrival when there is no window. A stop with no recorded arrival is not counted in either direction, and no grace period is invented. But the part that matters most is not the table: when any weighted input is unavailable the score must say which one. A retention score computed on nine of ten inputs must never be presented as ten.

The standard

One rule all eight are measured against

The Fuel Planner already does this correctly and is the reference every one of the eight is held to. It returns null rather than zero. It prints on the screen that the values are unavailable and are not zero. It returns a refusal on the detail rather than an empty page. It labels its fallback tank size as a fallback. Nobody looking at that screen can mistake missing for empty.

No silent empty. No zero that means unknown. No screen that shows nothing without saying why.

The full specification with the six create statements, every index, every linkage declaration and every guard is in GO-20, delivered to all seven seats. Every foreign key target in it was read from the live production database this morning and confirmed to exist: twenty tables, all keyed on id, except dispatch.cargo_sensor_readings, maintenance.brake_projections and maintenance.tire_projections, which key on uuid — a difference that would fail a migration on apply and cost a lane slot. mdata.units carries no company column, so unit queries scope through the row that does. None of the DDL was written from memory.
