SLICE A — BANK RECONCILIATION DRIFT ALERTS                       SEAT: CC-3
===============================================================================
Feature 1. Blocks the highest-value card on the owner home page after 425C.

WHY IT MATTERS
  Drift means the bank says one number and the books say another. Today nothing
  watches for it and nothing tells the owner. A carrier that finds a drift three
  months later cannot tell which of ninety days of transactions caused it.

WHAT EXISTS
  banking.reconciliation_sessions already computes and stores the variance:
    statement_balance_cents, book_balance_cents, variance_cents,
    adjusted_bank_balance_cents, adjusted_book_balance_cents, status,
    period_start, period_end, bank_account_id, finalized_at, voided_at
  banking.bank_accounts carries current_balance_cents, sync_status, last_synced_at.
  So the drift is already being measured. Nothing records it as an alert, and
  nothing watches balances between reconciliations.

DATA
  -- migration: create banking.reconciliation_drift_alerts
  CREATE TABLE IF NOT EXISTS banking.reconciliation_drift_alerts (
    id                        uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    operating_company_id      uuid NOT NULL REFERENCES org.companies(id),
    bank_account_id           uuid NOT NULL REFERENCES banking.bank_accounts(id),
    reconciliation_session_id uuid NULL REFERENCES banking.reconciliation_sessions(id),
    detected_at               timestamptz NOT NULL DEFAULT now(),
    as_of_date                date NOT NULL,
    drift_kind                text NOT NULL,      -- 'session_variance' | 'live_balance' | 'stale_feed'
    bank_balance_cents        bigint NOT NULL,
    book_balance_cents        bigint NOT NULL,
    drift_cents               bigint NOT NULL,
    tolerance_cents           bigint NOT NULL,
    severity                  text NOT NULL,      -- 'warning' | 'critical'
    resolved_at               timestamptz NULL,
    resolved_by_user_id       uuid NULL REFERENCES identity.users(id),
    resolution_note           text NULL,
    resolving_journal_entry_id uuid NULL REFERENCES accounting.journal_entries(id),
    voided_at                 timestamptz NULL,
    voided_by_user_id         uuid NULL REFERENCES identity.users(id),
    void_reason               text NULL,
    is_sample_data            boolean NOT NULL DEFAULT false,
    created_at                timestamptz NOT NULL DEFAULT now(),
    updated_at                timestamptz NOT NULL DEFAULT now()
  );
  -- one open alert per account per kind
  CREATE UNIQUE INDEX IF NOT EXISTS uq_drift_open_per_account_kind
    ON banking.reconciliation_drift_alerts (operating_company_id, bank_account_id, drift_kind)
    WHERE resolved_at IS NULL AND voided_at IS NULL;
  CREATE INDEX IF NOT EXISTS ix_drift_company_open
    ON banking.reconciliation_drift_alerts (operating_company_id, detected_at DESC)
    WHERE resolved_at IS NULL AND voided_at IS NULL;
  -- FORCED RLS + grants: apply the 0065 pattern verbatim.

  Tolerance lives in a setting, not a constant. Default 100 cents. Owner editable
  per bank account. Do not hard code it.

LINKAGE DECLARATION
  Links out to  : org.companies, banking.bank_accounts,
                  banking.reconciliation_sessions, identity.users,
                  accounting.journal_entries
  Linked in from: the owner attention panel, the banking board, the audit trail
  Hub coverage  : org.companies (company), identity.users (who resolved),
                  accounting.journal_entries (the correcting entry, when one is made)
  Financial     : a drift is not a posting. Resolving one MAY create a journal
                  entry; the alert records which one. It never posts by itself.

BACKEND
  A detector that runs after every reconciliation finalize and once nightly:
    session_variance — any finalized session where abs(variance_cents) > tolerance
    live_balance     — bank_accounts.current_balance_cents vs the ledger balance
                       for its ledger_account_id, computed from
                       accounting.journal_entry_postings, outside tolerance
    stale_feed       — last_synced_at older than 24 hours on an active account
  It opens an alert if none is open for that account and kind, and closes an
  alert automatically when the condition clears, recording who or what closed it.
  It NEVER posts a journal entry.

INTERFACE
  GET  /api/v1/banking/drift-alerts          list, filterable by resolved
  POST /api/v1/banking/drift-alerts/:id/resolve   requires a note

SCREEN
  Banking gains a Drift panel at the top: account, as of date, bank balance,
  book balance, the difference, and how long it has been open. Resolving requires
  a written reason. The owner attention card links here.

GUARD
  A test that finalizes a session with a variance above tolerance and asserts one
  alert opens; brings it back inside tolerance and asserts it closes with a reason.
  A test asserting the detector never writes to accounting.journal_entries.

PROOF
  One drift opened and closed in a browser, screenshotted, with the resolution note.

DONE MEANS
  The owner home page shows a real drift card, and every drift ever opened has a
  written resolution.

SLICE B — PREDICTIVE MAINTENANCE ALERTS                          SEAT: CC-3
===============================================================================
Feature 2.

WHY IT MATTERS
  Brake and tire projections are already being computed and stored. Nobody is
  ever told. A brake projected to hit its threshold in five days is a truck that
  goes out of service on the road instead of in the shop.

WHAT EXISTS
  maintenance.brake_projections: unit_uuid, brake_position, threshold_mm,
    current_thickness_mm, projected_replacement_date, wear_rate_mm_per_day, computed_at
  maintenance.tire_projections: unit_uuid, tire_position, threshold_32nds,
    current_depth_32nds, projected_replacement_date, wear_rate_32nds_per_day, computed_at
  Both live. The projection math is done. Only the alert layer is missing.

DATA
  CREATE TABLE IF NOT EXISTS maintenance.predictive_alerts (
    id                    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    operating_company_id  uuid NOT NULL REFERENCES org.companies(id),
    unit_id               uuid NOT NULL REFERENCES mdata.units(id),
    equipment_id          uuid NULL REFERENCES mdata.equipment(id),
    alert_type            text NOT NULL,                 -- 'brake_wear' | 'tire_tread'
    position_code         text NOT NULL,                 -- brake_position or tire_position
    source_projection_id  uuid NOT NULL,                 -- brake_projections.uuid or tire_projections.uuid
                                                       -- NOT a foreign key: it points at one of two
                                                       -- tables depending on alert_type. Enforce with
                                                       -- a check that the row exists in the matching
                                                       -- table, in the job, not in the schema.
    current_measure       numeric NOT NULL,
    threshold_measure     numeric NOT NULL,
    measure_unit          text NOT NULL,                 -- 'mm' | '32nds'
    projected_failure_date date NOT NULL,
    days_remaining        integer NOT NULL,
    severity              text NOT NULL,                 -- 'warning' | 'critical'
    work_order_id         uuid NULL REFERENCES maintenance.work_orders(id),
    resolved_at           timestamptz NULL,
    resolved_by_user_id   uuid NULL REFERENCES identity.users(id),
    resolution_note       text NULL,
    voided_at             timestamptz NULL,
    voided_by_user_id     uuid NULL REFERENCES identity.users(id),
    void_reason           text NULL,
    is_sample_data        boolean NOT NULL DEFAULT false,
    created_at            timestamptz NOT NULL DEFAULT now(),
    updated_at            timestamptz NOT NULL DEFAULT now()
  );
  CREATE UNIQUE INDEX IF NOT EXISTS uq_predictive_open_per_position
    ON maintenance.predictive_alerts (operating_company_id, unit_id, alert_type, position_code)
    WHERE resolved_at IS NULL AND voided_at IS NULL;
  CREATE INDEX IF NOT EXISTS ix_predictive_company_due
    ON maintenance.predictive_alerts (operating_company_id, projected_failure_date)
    WHERE resolved_at IS NULL AND voided_at IS NULL;
  -- FORCED RLS + grants: 0065 pattern.

LINKAGE DECLARATION
  Links out to  : org.companies, mdata.units, mdata.equipment,
                  maintenance.work_orders, identity.users,
                  and the source projection row
  Linked in from: the owner attention panel, the maintenance board, the unit profile
  Hub coverage  : org.companies, mdata.units, mdata.equipment,
                  maintenance.work_orders, identity.users
  Operational   : an alert that becomes a repair carries the work order id, so the
                  unit history shows prediction then repair as one chain.
  Financial     : none directly. The work order carries the money.

BACKEND
  A nightly job reads both projection tables, opens an alert where
  projected_replacement_date is within the alert horizon, and closes an alert when
  a newer projection clears it or a work order closes against that position.
  Horizon is a setting. Default: warning at 14 days, critical at 7.
  Opening a work order from an alert stamps work_order_id on the alert.

INTERFACE
  GET  /api/v1/maintenance/predictive-alerts
  POST /api/v1/maintenance/predictive-alerts/:id/create-work-order
  POST /api/v1/maintenance/predictive-alerts/:id/resolve

SCREEN
  Maintenance gains an At Risk panel: unit, position, current measure against
  threshold, projected date, days remaining, and a Create work order button.
  The unit profile shows its open alerts.

GUARD
  A test seeding a brake projection inside the horizon and asserting exactly one
  alert; clearing the measurement and asserting the alert closes.
  A test asserting alert_type is only brake_wear or tire_tread until a new type
  is added deliberately.

PROOF
  One alert raised from a real projection, a work order created from it, and the
  alert closing when the work order closes. Screenshotted.

DONE MEANS
  No brake or tire reaches its threshold without somebody having been told first.

SLICE C — ACCIDENT LIABILITIES                                   SEAT: CURSOR
===============================================================================
Feature 3. The highest-stakes of the eight. This one touches money, insurance and
a driver's pay, so it gets the strictest rules.

WHY IT MATTERS
  Today an accident is filed and nothing is ever created to decide who pays for it.
  safety.routes.ts line 553 hard returns a null liability id. There is no accident
  to liability to chargeback path at all. That means damage costs land nowhere,
  the driver is never charged or cleared, and the insurance recovery has no record
  to attach to.

WHAT EXISTS — AND THE PROOF THIS WAS ALWAYS THE DESIGN
  safety.accidents: driver_id, unit_id, accident_type, event_datetime,
    dot_reportable, injury_count, fatality_count, police_report_number, narrative
  safety.accident_cost_lines: accident_id, section, description, amount_cents
  insurance.claim ALREADY CARRIES A liability_id COLUMN, plus driver_responsible,
    deductible_cents, recovery_rail, repair_books_treatment, deduction_id.
  That FK column is pointing at a table that was never created. The chain was
  designed and only this link is missing.

DATA
  CREATE TABLE IF NOT EXISTS safety.accident_liabilities (
    id                      uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    operating_company_id    uuid NOT NULL REFERENCES org.companies(id),
    accident_id             uuid NOT NULL REFERENCES safety.accidents(id),
    incident_id             uuid NULL REFERENCES safety.incidents(id),
    driver_id               uuid NULL REFERENCES mdata.drivers(id),
    unit_id                 uuid NULL REFERENCES mdata.units(id),
    trailer_id              uuid NULL REFERENCES mdata.equipment(id),
    load_id                 uuid NULL REFERENCES mdata.loads(id),
    customer_id             uuid NULL REFERENCES mdata.customers(id),
    vendor_id               uuid NULL REFERENCES mdata.vendors(id),
    insurance_claim_id      uuid NULL REFERENCES insurance.claim(id),
    work_order_id           uuid NULL REFERENCES maintenance.work_orders(id),
    legal_matter_id         uuid NULL REFERENCES legal.matters(id),
    assessed_amount_cents   bigint NOT NULL,
    insurance_recovery_cents bigint NOT NULL DEFAULT 0,
    deductible_cents        bigint NOT NULL DEFAULT 0,
    net_exposure_cents      bigint NOT NULL,
    owner_decision          text NULL,   -- 'driver_chargeback' | 'company_absorbs' | 'insurance_only' | 'split'
    owner_decision_at       timestamptz NULL,
    owner_decision_by_user_id uuid NULL REFERENCES identity.users(id),
    owner_decision_note     text NULL,
    driver_charge_cents     bigint NOT NULL DEFAULT 0,
    company_absorb_cents    bigint NOT NULL DEFAULT 0,
    deduction_id            uuid NULL REFERENCES driver_finance.driver_settlement_deductions(id),
    journal_entry_id        uuid NULL REFERENCES accounting.journal_entries(id),
    expense_account_id      uuid NULL REFERENCES catalogs.accounts(id),
    status                  text NOT NULL DEFAULT 'open',  -- open|decided|posted|closed
    voided_at               timestamptz NULL,
    voided_by_user_id       uuid NULL REFERENCES identity.users(id),
    void_reason             text NULL,
    is_sample_data          boolean NOT NULL DEFAULT false,
    created_at              timestamptz NOT NULL DEFAULT now(),
    created_by_user_id      uuid NULL REFERENCES identity.users(id),
    updated_at              timestamptz NOT NULL DEFAULT now()
  );
  CREATE UNIQUE INDEX IF NOT EXISTS uq_liability_per_accident
    ON safety.accident_liabilities (operating_company_id, accident_id)
    WHERE voided_at IS NULL;
  CREATE INDEX IF NOT EXISTS ix_liability_awaiting_owner
    ON safety.accident_liabilities (operating_company_id, created_at DESC)
    WHERE owner_decision IS NULL AND voided_at IS NULL;
  -- FORCED RLS + grants: 0065 pattern.
  -- Then, and only then, wire insurance.claim.liability_id to this table.

LINKAGE DECLARATION
  Links out to  : org.companies, safety.accidents, safety.incidents, mdata.drivers,
                  mdata.units, mdata.loads, mdata.customers, mdata.vendors,
                  maintenance.work_orders, insurance.claim, legal.matters,
                  driver_finance.driver_settlement_deductions,
                  accounting.journal_entries, catalogs.accounts, identity.users
  Linked in from: insurance.claim.liability_id, the owner attention panel,
                  the driver settlement, the safety board, the unit history
  Hub coverage  : every hub table except docs.files and mdata.equipment, which
                  attach through safety.accidents evidence
  Operational   : safety, insurance, legal, maintenance, dispatch, driver, unit,
                  trailer and load all reachable in one hop.
  Financial     : the liability is the record that decides who pays. It carries
                  the deduction it created and the journal entry it posted.

BACKEND — READ THIS PART TWICE
  Filing an accident creates a liability in status open with a null owner_decision,
  assessed from safety.accident_cost_lines. It posts NOTHING.
  The owner decides. Only the owner. The decision is what moves money:
    driver_chargeback -> creates a PENDING deduction in
                         driver_finance.driver_settlement_deductions, load_id
                         carried through, status held until approved. It is never
                         automatic and never silent.
    company_absorbs   -> posts the expense to the account named on the liability
    insurance_only    -> no driver charge, deductible posts as company expense
    split             -> both, and driver_charge_cents plus company_absorb_cents
                         must equal net_exposure_cents exactly
  net_exposure_cents = assessed_amount_cents - insurance_recovery_cents.
  A liability with no owner_decision NEVER posts and NEVER creates a deduction.

INTERFACE
  GET  /api/v1/safety/accident-liabilities
  POST /api/v1/safety/accident-liabilities/:id/decide   owner role only

SCREEN
  Safety gains an Awaiting your decision panel. Each row: accident, driver, unit,
  load, assessed amount, insurance recovery, net exposure, and the four choices
  with a required note. The driver settlement shows the resulting deduction as
  pending until approved. The owner attention card links here.

GUARD
  A test that files an accident and asserts a liability with a null decision and
  zero postings.
  A test that a decision of split refuses unless the two amounts equal the net.
  A test that a non owner role cannot call decide.
  A test that a driver deduction from a liability is created pending, never applied.
  A test that voiding a liability voids its deduction and reverses its entry,
  and that neither is ever hard deleted.

PROOF
  One accident filed, the liability appearing with no decision, the owner deciding
  driver chargeback, and the pending deduction appearing on that driver's
  settlement. Every step screenshotted.

DONE MEANS
  No accident cost lands nowhere, and no driver is ever charged without the owner
  deciding it in writing.

SLICE D — CARGO SENSOR INCIDENTS                                 SEAT: CC-2
===============================================================================
Feature 4.

RECOMMENDATION ON WHERE IT LIVES — one word from the owner if you disagree.
  The aggregator queries telematics.cargo_sensor_incidents. The readings it must
  group live in dispatch.cargo_sensor_readings. Put the incidents beside their own
  readings, in dispatch, and repoint the aggregator. Splitting a reading from its
  incident across two schemas is the fragmentation the linkage law exists to stop.
  If the owner prefers telematics, it is a one word change to the DDL and one line
  in the aggregator.

WHAT EXISTS
  dispatch.cargo_sensor_readings: load_uuid, trailer_uuid, sensor_id, temp_celsius,
    humidity_pct, door_status, reading_at, out_of_range
  The out_of_range flag is already being written. Nothing groups the readings into
  an incident and nothing tells anybody.

Feature 11. The retention score is currently wrong and says nothing about it.

WHY IT MATTERS
  The retention risk score carries a weighted late arrival input. The table it
  reads does not exist, the feature comes back null, the scorer skips nulls, and
  the dashboard filters the factor out of the contributing factors list. So the
  score shown is computed on fewer inputs than it claims and nothing says so.
  A risk number quietly missing a weighted input is worse than no number.

WHAT EXISTS
  dispatch.stop_arrivals: stop_id, unit_id, driver_id, triggered_at, confirmed_at
  mdata.load_stops: appointment_start_at, appointment_end_at, scheduled_arrival_at,
    actual_arrival_at, time_window_type, stop_type, load_id
  Everything needed to define late is already recorded.

THE DEFINITION OF LATE — agree this before writing code
  If the stop has an appointment window, late means actual_arrival_at is after
  appointment_end_at.
  If it has no window, late means actual_arrival_at is after scheduled_arrival_at.
  If actual_arrival_at is null the stop is not counted at all, in either direction.
  A stop with no schedule and no appointment is not counted.
  Do not invent a grace period. If the owner wants one it is a setting.

DATA
  CREATE TABLE IF NOT EXISTS dispatch.late_arrival_aggregates (
    id                    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    operating_company_id  uuid NOT NULL REFERENCES org.companies(id),
    driver_id             uuid NOT NULL REFERENCES mdata.drivers(id),
    bucket_date           date NOT NULL,
    stops_measured        integer NOT NULL,
    stops_late            integer NOT NULL,
    late_pct              numeric NOT NULL,
    avg_minutes_late      numeric NULL,
    worst_minutes_late    integer NULL,
    basis                 text NOT NULL,   -- 'appointment_window' | 'scheduled_arrival' | 'mixed'
    computed_at           timestamptz NOT NULL DEFAULT now()
  );
  CREATE UNIQUE INDEX IF NOT EXISTS uq_late_arrival_driver_day
    ON dispatch.late_arrival_aggregates (operating_company_id, driver_id, bucket_date);
  CREATE INDEX IF NOT EXISTS ix_late_arrival_recent
    ON dispatch.late_arrival_aggregates (operating_company_id, bucket_date DESC);
