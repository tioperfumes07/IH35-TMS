# TBL-STANDARD (DB Table Standard) — Sweep vs Live Guard Coverage

**Docs-only. Read-only reconciliation.** No schema change, no migration, no code in this block.

## Naming collision — flagged per house drift-prevention rule (§9)

`TBL-STANDARD` is **already a name in use in this repo** for a different, unrelated thing: the
**shared-DataTable UI list-surface migration** (bespoke list pages → the shared `DataTable` component +

in-flight `tbl-standard-sweep-batch1`/`batch2` worktrees at the time of writing). That work is about
**frontend rendering**, not database schema.

**This document is about a different standard** — the per-**database-table** entity-scoping / audit /
soft-delete / linkage bar every table in this schema is held to. To avoid colliding with the existing
UI-sweep name, treat this doc's subject as **"TBL-STANDARD (DB)"** wherever the two could be confused.
If a future agent lands on this file looking for the DataTable UI sweep, it is the wrong document —
see `docs/specs/qbo-parity/00_INDEX.md` and the PRs above instead.

## The standard (four pillars)

A table meets the DB standard when it satisfies all of:

1. **Entity scoping** — a `uuid` scoping column (`operating_company_id`, or the verified-live synonyms
   `tenant_id` / `company_id`) with an FK to `org.companies(id)`, an RLS policy that actually scopes by
   that column (single-entity equality **or** accessible-companies membership — both are correct, see
   below), and `FORCE ROW LEVEL SECURITY`. This is the exact four-part test
   `scripts/verify-entity-isolation.mjs` enforces (full spec: `docs/ci-guards/ENTITY-ISOLATION.md`).
2. **Audit** — every table gets an append-only trail. Two live mechanisms cover this depending on the
   table's role: `audit.row_changes` (generic row-level change capture) and the `events.log_event()` /
   `audit.audit_events` spine (business-event capture, hash-chained — see `verify:audit-chain-verify`,
   `verify:event-log-worm`). Enforced piecemeal today by module-scoped guards
   (`verify:a1-audit-spine-link` through `verify:a8-audit-reports-section`, `verify:audit-coverage`,
   `verify:row-changes-evidence-coverage`, `verify:db-verify-audit-append-only`,
   `verify:db-verify-phase1-audit-coverage`) rather than one single cross-schema introspection sweep.
3. **`is_active` (void-not-delete)** — per constitution §2, every table gets `is_active` (or an
   equivalent soft-delete marker: `voided_at`, `soft_deleted_at`, `deactivated_at`, `archived_at` are
   all live variants of the same convention across `mdata.*`/`accounting.*`). `DELETE` is never used on
   business data. Enforced by targeted guards per table family (e.g.
   `verify:equipment-deactivate-rls`, `verify:civil-fines-voidable`) rather than a single universal
   sweep.
4. **Cross-module linkage** — per the ★ Law of the Land (10a), every financial primitive links forward
   and backward to its operational context (load, vendor, customer, driver, unit) and every operational
   record links to its financial trace. Enforced by narrow per-relationship guards
   (`verify:wo-bill-expense-hard-fk-link`, `verify:fk-integrity-fault-da-records`,
   `verify:task-link-contract`, `verify:orphan-components`, etc.), not one cross-schema sweep.

**Only pillar 1 has a single, general, live, self-updating introspection guard today** —
`verify-entity-isolation.mjs`. Pillars 2–4 are real, but enforced as a constellation of narrower,
targeted CI guards rather than one universal table-level sweep. That is an honest gap, not a claim this
doc closes — see "What this doc does NOT do" below.

## Verdict

**Largely already enforced**, consistent with the task framing: 446 of 581 non-exempt business tables
(656 total minus 75 global-exempt; ~77%) are fully compliant with pillar 1 today, continuously verified
by a live, self-regenerating CI
guard that fails the build the instant a new table ships un-walled or an already-compliant table
regresses. The remaining 135 are tracked debt with a phase and a specific missing-requirement reason
each — not silent gaps. Pillars 2–4 (audit / is_active / linkage) are real and enforced, but by many
narrower guards rather than one equivalent cross-schema sweep; unifying them into one
`verify-tbl-standard.mjs`-style introspection guard (modeled on `verify-entity-isolation.mjs`'s
four-requirement pattern) would be a reasonable follow-up block, **not** built here — it would require
schema/migration decisions (e.g. deciding the canonical soft-delete column name per table family) that
are financial-cluster-adjacent and out of scope for a docs-only, non-financial block.

## What this doc does NOT do

- Does not run a live introspection query (no DB access in this worktree; the committed allowlist +
  guard are the live source of truth, verified continuously in CI).
- Does not close any backlog entry. Closing one means walling the table (migration + RLS +
  `--update`), which is schema-cluster work requiring the standard show-the-SQL-first protocol and,
  for `accounting.*`/`catalogs.*` tables, Jorge's explicit OK before merge (constitution §1.3/§1.4).
- Does not propose new pillar-2/3/4 guards. Names the gap; does not fill it.
