ROOT CAUSE — and a VERIFIED CORRECTION to the audit, because it matters:
The lists audit flagged the fleet `+ Create` path as "silent field loss — metadata accepted by the
zod schema, sent by the modal, never inserted (RETURNING hardcodes '{}'::jsonb AS metadata)". I
verified each half against the PROD branch before touching it, and the audit was OVERSTATED in one
direction and precise in the other:

  * PROD (information_schema, 2026-07-24): NONE of the nine fleet catalog tables — tractor_statuses,
    trailer_statuses, asset_condition_codes, equipment_types, unit_ownership_types, trailer_types,
    lease_terms, asset_statuses, asset_locations — has a `metadata` column. So the field was not
    "lost on the way to a column"; there was never a column.
  * The FleetCatalogModal renders NO metadata input (only code / display_name / description /
    sort_order / is_active). `metadata: row?.metadata ?? {}` was dead form-state. So there is no
    OPERATOR data loss — no one types metadata that vanishes.
  * What IS real: the create/update zod schemas ACCEPTED `metadata`, so an API caller could send it
    and have it silently discarded — the DoD Layer-C "accepted by the API is not persisted" lie —
    and the RETURNING advertised a metadata capability the schema never had.

FIX (in-lane, NO migration — the honest, minimal change):
  * Removed `metadata` from the create and update zod schemas — the API no longer accepts a field it
    cannot store. zod strips the modal's vestigial metadata:{} payload silently, so no request breaks.
  * Kept `'{}'::jsonb AS metadata` in the RETURNING for frontend response-shape stability, annotated
    as stable-empty / contract-compat only (removing it from the response would churn the FE type for
    no gain).
  * Removed the dead `metadata` form-state from FleetCatalogModal.

Deliberately NOT changed, because prod says the audit's premise is wrong: the "global uniqueness
blocks USMCA" finding. These nine tables have NO operating_company_id column — they are GLOBAL/shared
catalogs by design, so a globally-unique code is correct and USMCA uses the shared row rather than
needing its own. Whether fleet status/type catalogs SHOULD be per-entity is an owner/product decision
(it needs an operating_company_id migration across nine tables), not a bug to fix unilaterally.
